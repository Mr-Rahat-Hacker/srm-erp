# SRM PostgreSQL Logical Data Dictionary

**Document ID:** SRM-DB-001  
**Version:** 1.0  
**Status:** Proposed logical design — review required  
**Date:** 21 November 2026

## 1. Purpose and design boundary

This document defines the proposed logical relational model for the first-release SRM application. It is based on the SRS, supplier/RFQ workflow, RBAC matrix, audit specification and detailed business-requirements review.

The model stores SRM-owned workflow data. SAP remains the system of record for Vendor Master / Business Partner and Material Master. The SRM database stores an authorized mapping to an existing SAP Vendor Code and SAP Material Code references used by RFQ lines; it does not create SAP vendor or material master records.

This is a logical design, not an executable migration. Exact field lengths, constraints, indexes, retention, encryption and policy configuration must be reviewed before implementation.

## 2. Conventions

- PostgreSQL schema: `srm`.
- Primary keys: UUID, generated by the application or database.
- Timestamps: `TIMESTAMPTZ`, stored and interpreted in UTC.
- Monetary values: `NUMERIC(18,2)` for totals and `NUMERIC(18,4)` for unit rates; never floating-point.
- Currency: ISO 4217 code, normally `CHAR(3)`.
- Status values: controlled codes; use lookup/configuration tables or validated enums rather than arbitrary UI text.
- Business records use `created_at`, `created_by`, `updated_at`, `updated_by` where applicable.
- Historical decisions and submitted quotation versions are retained; do not overwrite history.
- File bytes should live in approved object storage. PostgreSQL stores metadata and a storage key, not public file URLs.

## 3. Identity and access tables

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `app_user` | Internal and supplier user accounts | `user_id PK`, normalized unique `email`, `password_hash`, `full_name`, `account_status`, timestamps |
| `role` | Seven approved application roles | `role_id PK`, unique `role_code`: SUPER_ADMIN, SRM_ADMIN, SUPPLIER_USER, SUPPLIER_VERIFIER, PROCUREMENT_BUYER, PROCUREMENT_APPROVER, AUDITOR |
| `permission` | Fine-grained backend permissions | `permission_id PK`, unique `permission_code`, description |
| `role_permission` | Role-to-permission mapping | Composite PK `(role_id, permission_id)` |
| `user_role` | User role assignments | Composite PK `(user_id, role_id)`; assigned_by and assigned_at; changes audited |
| `supplier_user_membership` | Links supplier accounts to their supplier organization | Composite PK `(supplier_id, user_id)`; membership status; supplier data isolation enforced in services |

A user may hold multiple roles only under organizational policy. Approval authority is additionally constrained by assigned approval tasks and approval rules; role membership alone is insufficient.

## 4. Supplier and qualification tables

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `supplier_organization` | SRM supplier master/profile | `supplier_id PK`, unique `supplier_number`, legal/trade name, GSTIN, PAN, lifecycle status, category and capability attributes |
| `supplier_address` | Registered, communication and other addresses | `address_id PK`, `supplier_id FK`, address_type, address fields, country_code, is_primary |
| `supplier_contact` | Supplier contact persons | `contact_id PK`, `supplier_id FK`, name, email, phone, designation, contact_type |
| `supplier_bank_account` | Supplier bank details, if approved for Phase 1 | `bank_account_id PK`, `supplier_id FK`, encrypted/suitably protected account data, verification status; strict field-level access and audit |
| `supplier_document` | Document metadata and storage reference | `document_id PK`, `supplier_id FK`, document_type, storage_key, file metadata, version, review_status, expiry_date |
| `supplier_document_review` | Document-level verification decisions | `review_id PK`, `document_id FK`, reviewer, decision, remarks, decided_at |
| `supplier_review` | Staged supplier review/qualification | `review_id PK`, `supplier_id FK`, review_stage (SCM/Finance/Quality/final as configured), reviewer, decision, remarks, decided_at |
| `supplier_status_history` | Supplier lifecycle transition history | `history_id PK`, supplier_id, old_status, new_status, actor, reason, changed_at |
| `sap_vendor_mapping` | Mapping to an existing SAP vendor | `mapping_id PK`, supplier_id FK, SAP system identifier, SAP vendor code, active flag, mapped_by, mapped_at; uniqueness per SAP system/vendor code |

Supplier bank details are sensitive. Their inclusion, access, retention and verification requirements must be confirmed before enabling this table in production. Store only the data genuinely required.

## 5. SAP reference data

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `sap_system` | Configured SAP system/connection identity | `sap_system_id PK`, system_code, environment, active flag; no credentials stored in ordinary table fields |
| `sap_material_reference` (optional cache) | Read-only cached SAP material reference for search/display | SAP system, material code, description, base UOM, plant references, last_synced_at; never an SRM-owned material master |

If SAP material lookup is performed live and no local cache is needed, omit `sap_material_reference`; retain the SAP material code as a reference on each RFQ line.

## 6. RFQ and invitation tables

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `rfq` | RFQ header | `rfq_id PK`, unique rfq_number, buyer, title, project/department/plant/purchasing group, currency, deadline, required delivery date, payment terms, Incoterms, status |
| `rfq_line` | Requested items/services | `rfq_line_id PK`, rfq_id FK, line_number, SAP material code, description, drawing/revision reference, quantity, UOM, plant, technical specifications |
| `rfq_attachment` | RFQ drawings/specifications/T&Cs | `attachment_id PK`, rfq_id FK (and optional line FK), storage_key, filename, content_type, uploaded_by |
| `rfq_invitation` | Supplier invitation and response | `invitation_id PK`, rfq_id FK, supplier_id FK, invitation_status, invited_at, acknowledged_at, decline_reason; unique (rfq_id, supplier_id) |
| `rfq_status_history` | RFQ lifecycle history | `history_id PK`, rfq_id FK, old_status, new_status, actor, reason, changed_at |

RFQ line `sap_material_code` is a reference to SAP-owned material data. The SRM application must not create or maintain Material Master records.

## 7. Quotation and evaluation tables

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `quotation` | Supplier's response identity for one RFQ | `quotation_id PK`, rfq_id FK, supplier_id FK, current_version_id, lifecycle_status; unique (rfq_id, supplier_id) unless policy permits multiple responses |
| `quotation_version` | Immutable submitted quotation revision | `quotation_version_id PK`, quotation_id FK, version_number, submitted_by, submitted_at, currency_code, validity_date, payment terms, Incoterms, lead time, MOQ, warranty, status; unique (quotation_id, version_number) |
| `quotation_line` | Supplier's commercial response per RFQ line | `quotation_line_id PK`, quotation_version_id FK, rfq_line_id FK, basic_unit_price, discount, net_unit_price, tax, freight, packing, tooling, insurance, other_charges, landed_line_total |
| `quotation_charge` | Extensible additional charge components | `charge_id PK`, quotation_line_id or quotation_version_id FK, charge_type, amount, tax treatment, description |
| `quotation_attachment` | Supplier quote and supporting files | `attachment_id PK`, quotation_version_id FK, storage_key, file metadata |
| `technical_evaluation` | Technical assessment and outcome | `technical_evaluation_id PK`, quotation_version_id FK, evaluator, status, remarks, evaluated_at |
| `commercial_evaluation` | Commercial scoring/comparison | `commercial_evaluation_id PK`, quotation_version_id FK, evaluator, comparison_basis, score/rank where configured, remarks |
| `evaluation_criterion` | Configurable evaluation criteria | `criterion_id PK`, criterion_code, name, evaluation_type, active flag |
| `evaluation_result` | Result per criterion and quotation version | `result_id PK`, criterion_id FK, quotation_version_id FK, result/value, evaluator, remarks |

Quotation revisions are immutable after submission. A revision is inserted as a new version; the prior version remains queryable. Supplier-facing authorization must prevent access to other suppliers' quotation data.

## 8. Negotiation, recommendation and award tables

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `negotiation_round` | Negotiation round for an RFQ/supplier | `negotiation_round_id PK`, rfq_id FK, supplier_id FK, round_number, status, opened_at, closed_at; unique (rfq_id, supplier_id, round_number) |
| `negotiation_message` | Buyer/supplier negotiation communications | `message_id PK`, negotiation_round_id FK, sender_user_id, message_type, message_text, created_at |
| `supplier_recommendation` | Buyer's supplier/rate recommendation | `recommendation_id PK`, rfq_id FK, supplier_id FK, quotation_version_id FK, recommended_by, justification, is_non_l1, created_at |
| `approval_request` | Approval process linked to a business record | `approval_request_id PK`, entity_type, entity_id, workflow_code, status, requested_by, created_at |
| `approval_task` | Individual approval stage/assignment | `approval_task_id PK`, approval_request_id FK, stage_code, assigned_user_id or group, sequence_no, status, due_at |
| `approval_decision` | Immutable decision event | `decision_id PK`, approval_task_id FK, actor_user_id, decision, remarks, decided_at |
| `award` | Approved supplier award | `award_id PK`, rfq_id FK, supplier_id FK, quotation_version_id FK, approval_request_id FK, approved_value, currency_code, status, awarded_at |
| `award_amendment` | Controlled post-award amendment | `amendment_id PK`, award_id FK, amendment_number, reason, proposed_changes, approval_request_id FK, status, created_at |

Approval routing and monetary thresholds must be configuration data, not hard-coded values. A non-L1 recommendation requires justification and the configured exception approval path. Award creation is permitted only after required approvals.

The generic `approval_request.entity_type/entity_id` pair is a polymorphic reference. Application services must validate that the referenced business record exists and is in an approvable state.

## 9. Workflow configuration tables

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `approval_workflow` | Named approval workflow definition | `workflow_id PK`, workflow_code, version, entity_type, active_from, active_to, status |
| `approval_workflow_stage` | Ordered stages in a workflow | `stage_id PK`, workflow_id FK, stage_code, sequence_no, approver_group, mandatory_flag |
| `approval_rule` | Conditions selecting workflow/routes | `rule_id PK`, workflow_id FK, plant/category/value/deviation conditions, priority, active flag |
| `supplier_document_type` | Configured document requirements | `document_type_id PK`, code, name, mandatory_flag, expiry_required |
| `supplier_review_stage_config` | Configured supplier review stages | `stage_config_id PK`, stage_code, sequence_no, applicable_supplier_category, mandatory_flag |

Workflow rules and approval limits must be versioned so a later configuration change does not rewrite the meaning of an approval already in progress.

## 10. Notifications, audit and integration tables

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `notification` | In-app/email notification queue and status | `notification_id PK`, recipient_user_id, event_type, channel, delivery_status, retry_count, created_at, sent_at |
| `notification_attempt` | Delivery attempt history | `attempt_id PK`, notification_id FK, attempted_at, outcome, provider_reference, error_code |
| `audit_event` | Append-only security/business event | `audit_event_id PK`, occurred_at, actor_user_id, actor_type, effective_roles, action_code, entity_type, entity_id, supplier_id, rfq_id, quotation_id, approval_request_id, outcome, reason, changed_fields, correlation_id |
| `integration_event` | Outbound/inbound integration tracking | `integration_event_id PK`, target_system, operation_type, business_reference, request_correlation_id, status, attempted_at, response_code, sanitized_error |
| `sap_pir_sync_request` | Controlled PIR/rate/condition write request | `sync_request_id PK`, supplier_id FK, SAP vendor code reference, SAP material code, purchasing organization/plant, proposed rate/conditions, approval_request_id FK, status, external_reference |

Audit rows are append-only through application permissions and database controls. Critical business transitions should write audit events transactionally where feasible. SAP integration must use authorized SAP APIs or middleware; direct SAP database writes are prohibited. Secrets and tokens must never be stored in audit or integration payload logs.

## 11. Core relationship summary

- One supplier organization can have multiple supplier users, addresses, contacts and documents.
- One supplier can have multiple review records and SAP vendor mappings over time, with only the permitted active mapping(s).
- One RFQ has one or more RFQ lines and can invite multiple suppliers.
- One supplier invitation belongs to one RFQ and one supplier.
- One RFQ/supplier pair normally has one quotation aggregate with one or more immutable versions.
- One quotation version has one or more quotation lines, each referencing an RFQ line.
- Evaluation, negotiation and recommendation records are linked to the relevant RFQ, supplier and quotation version.
- An approval request has one or more ordered approval tasks; each decision is separately retained.
- An award references the selected supplier, exact quotation version and completed approval request.
- Audit events correlate relevant entities but are not deleted when business records change.

## 12. Key constraints and indexes to implement

1. Unique normalized user email.
2. Unique supplier number.
3. Unique RFQ number.
4. Unique RFQ line number within RFQ.
5. Unique supplier invitation per RFQ/supplier.
6. Unique quotation aggregate per RFQ/supplier unless a confirmed policy permits multiple quotations.
7. Unique quotation version number per quotation.
8. Unique negotiation round number per RFQ/supplier.
9. Unique SAP vendor code per SAP system where the SAP business rule requires it.
10. Index foreign keys and common filters: supplier status, RFQ status/deadline, invitation supplier/status, quotation RFQ/supplier, approval assignee/status/due date, audit timestamp/actor/entity/correlation ID.
11. Use check constraints for positive quantities, non-negative charge values where applicable, valid status codes and valid monetary precision.
12. Use optimistic locking/version columns on mutable business aggregates where concurrent updates are possible.
13. Enforce quotation immutability after submission through service logic and database-level protections for critical tables.
14. Restrict updates/deletes on audit_event; consider database triggers and separate database privileges for production hardening.
15. Use composite indexes and tenant/supplier scoping to support secure supplier data isolation.

## 13. Open design decisions before SQL migrations

- Confirm whether supplier bank account details belong in Phase 1 and which roles can view them.
- Confirm whether one RFQ/supplier pair may submit multiple independent quotations or only revisions of one quotation.
- Confirm the landed-cost calculation formula, tax inclusion and charge allocation across RFQ lines.
- Confirm technical/commercial bid opening policy and who may access commercial values before technical acceptance.
- Confirm approval task assignment to an individual, group, or both, and delegation rules.
- Confirm whether the SAP Vendor Code mapping is mandatory for RFQ eligibility.
- Confirm whether a local read-only SAP material reference cache is required.
- Confirm file storage provider, malware scanning, retention and access URL strategy.
- Confirm audit retention, partitioning, archival and legal-hold requirements.
- Confirm approval configuration versioning and post-award amendment policy.
